# Phoenix Spec & Regeneration Workflow

本技能将传统“阅读并修补代码”的工作流转化为“提炼不变意图与验证基准 -> 丢弃旧实现 -> 双盲再生新实现”的可再生工程流。

## 核心架构原则
1. **步调层级（Pace Layers）隔离**：只提取变化极慢的核心领域模型、状态机、外部契约与业务不变量（Slow Layer）；坚决过滤内部私有函数、框架绑定语法和临时优化技巧（Fast Layer）。
2. **评估即源码（Evals as Source Code）**：任何未转化为黑盒输入/输出断言的文字描述都是不可靠的。Spec 必须配套可执行的黑盒测试集。
3. **删除测试（Deletion Test）**：Spec 完备性的唯一标准是——在完全隔离原代码的前提下，仅凭 Spec 再生出的新代码能够 100% 通过原代码的黑盒测试基准。

## 执行阶段（必须按顺序执行）

### Phase 1: 划定“可再生粒度（Regenerative Grain）”
- 确认目标代码单元的业务边界。如果模块过于庞大（耦合多个独立业务领域），先将其拆分为高内聚的独立子单元再逐一提取。

### Phase 2: 提炼不变规范 (`spec.md`)
读取目标源代码，输出结构化的 `spec.md`，必须包含以下模块：
1. **Intent & Boundaries**：一句话核心职责、外部输入源与外部副作用清单。
2. **Public Contracts**：剥离语言特性的公开接口签名、数据结构约束与错误码协议。
3. **Domain State Machine**：合法状态集合、状态转换触发条件与非法跃迁禁令。
4. **Business Invariants (`BR-01` ~ `BR-N`)**：使用 `Given-When-Then` 格式逐条列出所有正常流、分支条件与隐性边界逻辑（如空值、精度、幂等性、并发约束）。
5. **Suspected Legacy Workarounds**：单独列出疑似针对过时依赖或旧环境的防御性补丁，标记为 `[NEEDS_HUMAN_REVIEW]`，不默认写入核心规则。

### Phase 3: 构建黄金评估集 (`golden_evals`) 与基线校准
- 严格依据 `spec.md` 编写黑盒测试套件（只调用公开入口，**严禁 Mock 或访问任何内部私有方法/属性**）。
- **基线校准**：先针对**现有原始代码**运行该黑盒测试套件。若原代码未通过测试，说明 `spec.md` 提炼存在偏差，必须回溯修正 `spec.md` 直至原代码 100% 通过。

### Phase 4: 双盲再生与删除测试（Blind Regeneration & Deletion Test）
- **上下文隔离**：在不参考原代码实现结构的前提下，仅读取 `spec.md` 从零生成全新的核心功能实现。
- **执行删除测试**：将 Phase 3 的黄金评估集指向新生成的代码运行：
  - **全部通过**：声明该模块已具备“可再生性”，输出最终 `spec.md`、测试套件与再生代码。
  - **存在失败用例**：对比失败用例在原代码与再生代码上的行为差异，定位 `spec.md` 中遗漏的隐性规则，补充新的 `BR-XX` 条款后重新执行 Phase 4，直至 100% 通过。

## 质量红线（Strict Guardrails）
- **禁止泄漏实现细节**：`spec.md` 中不得出现原代码的内部私有变量名、内部辅助函数名或特定框架类名。
- **禁止白盒断言**：黄金评估集只能断言公开返回值、抛出的标准异常或外部接口副作用，禁止检查内部状态字段。
